# Testing

How a change to this repository is tested: the action harness on every pull request, the container checks, the canary lecture repository, and what you can run locally. The last section says what none of them covers.

| Where | What it tests | When it runs |
|---|---|---|
| [`test-actions.yml`](../../.github/workflows/test-actions.yml), the action harness | Each action at the pull request's commit, the templates' hand-offs between jobs, and the user manual | Every pull request, every push to `main`, and by hand |
| [`validate-containers.yml`](../../.github/workflows/validate-containers.yml), called by the harness | Each image a pull request changes, built as a `pr-<N>` candidate and smoke-tested | Within the harness, on a pull request that changes an image |
| [`test-container.yml`](../../.github/workflows/test-container.yml) | The smoke test and size report, on an image's candidates before they can reach `:latest` | Called by `validate-containers.yml` on a pull request's candidates and by `build-containers.yml` on main's, before it promotes them; and by hand for any tag |
| [`test-containers-lectures.yml`](../../.github/workflows/test-containers-lectures.yml) | Four lecture repositories built in both images | After each promotion to `:latest`, weekly on Monday at 02:00 UTC, and by hand, as at a release candidate that changes what a build reports |
| [QuantEcon/test-actions-lecture-intro](https://github.com/QuantEcon/test-actions-lecture-intro), the canary | A release, in a real lecture repository running `templates/`, with real deploys | On its own pull requests, weekly on Sunday, once after each `v0` move, and for what the release gate does not reach |
| [`gate.yml`](https://github.com/QuantEcon/test-actions-lecture-intro/blob/main/.github/workflows/gate.yml) in the canary, the release gate | A release candidate, checked out and run on a frozen fixture: the cache build, both restores, both previews and a GitHub Pages deploy | By hand, on the canary's `main`, before `v0` moves |
| [`canary-watch.yml`](../../.github/workflows/canary-watch.yml), the canary's watcher | That each of the canary's scheduled workflows, `cache.yml`, `ci.yml` and `publish.yml`, is enabled, and that its newest scheduled run succeeded and is at most eight days old; and that the canary's workflows match `templates/` at `v0`, apart from the differences [`.github/canary-drift.yml`](../../.github/canary-drift.yml) declares. Both are read through the API, and a red verdict on the schedule opens or comments on an issue here | Daily at 06:30 UTC, and by hand |

## The action harness

`test-actions.yml` calls each action as `uses: ./<action>`, so it tests the code on the pull request, not a released tag. Its required check is `Action harness: all checks`.

### The gate

The workflow has no `paths:` filter: a filtered-out workflow publishes no check run, and a required check would then wait forever. Instead its first job, `gate`, decides whether the change can affect the actions:

- **`IGNORED`** is a list of paths that cannot, such as the root docs, `docs/`, `tests/` and `templates/`. It is an ignore list, not a cover list, so a path it does not recognise runs the whole harness: forgetting to extend it costs CI minutes, never a green check earned by running nothing.
- **A self-test** fails the gate if `IGNORED` would match any file the harness must run for: each action's `action.yml`, which it reads from the workflow's own `uses: ./<action>` lines, the shared scripts and lockfiles, and the container files. It also checks that `IGNORED` still matches the paths it is meant to.
- **The checks a docs-only change still needs** run in the gate itself, because such a change skips every other job: the templates pin the same third-party actions as `.github/workflows/`, and `scripts/generate-docs.py --check --check-examples --actionlint` finds the manual's generated tables current, a chapter for every action and for every reusable workflow a lecture repository calls (`on.workflow_call`), and every example valid. [CHAPTER-TEMPLATE.md](CHAPTER-TEMPLATE.md) lists those checks.
- **actionlint over `.github/workflows/`** runs in the gate too, on every event, so a problem in any workflow fails the required check. actionlint lints each `run:` script with shellcheck, and silently skips them when it finds none, so the gate fails when the runner image has no shellcheck, and logs both tools' versions. An ignore goes in `.github/actionlint.yaml`, which actionlint reads by default, limited to one file and saying why.
- **shellcheck over the actions' `run:` scripts and `scripts/*.sh`** runs in the gate as well, through [`scripts/lint-shell.py`](../../scripts/lint-shell.py), because actionlint never reads an `action.yml`. It fails on any `${{ }}` in a `run:` script, an action's or a workflow's, since a value belongs in the step's `env:`, and on any shellcheck finding of warning severity or above, reported at its line in `action.yml`. The container scripts under `containers/` are left out, since a change there rebuilds both images.

`harness-summary`, the job behind `Action harness: all checks`, passes only if the gate succeeded and either every job succeeded, when the gate found the change relevant, or every job was skipped, when it did not. Any other mix fails it.

### Fixtures

- **`.github/fixtures/mini-lectures/`**: a two-page book with a code cell that really executes, so a build writes a genuine `_build/.jupyter_cache`. Cache keys are salted with the run's id and attempt, so one run's caches cannot satisfy another's miss assertions.
- **`.github/fixtures/access-gate/server.py`**: a local stand-in for a Cloudflare Access gate, which answers in every shape the `deploy-cloudflare` gate probe has to tell apart, over TLS when a job needs it.
- **`.github/fixtures/preview-comment/`**: the comment bodies the preview actions must render for given inputs, and a stand-in for GitHub's API that the comment script runs against.
- **`.github/fixtures/preview-toc/`**: two sites' `_toc.yml`, copied from QuantEcon/lectures, a pull request's files, and what each toc must list from them, which `preview-change-detection` and `preview-comment` both assert, for `toc-file`.
- **`.github/fixtures/release-stub/gh`**: a stand-in for the `gh release view` and `gh release download` calls `restore-gh-pages` makes, serving releases from a directory, and recording any call it does not expect.

The container smoke fixture in `containers/quantecon/tests/` is separate: it tests an image, not the actions. See [CONTAINERS.md](CONTAINERS.md#the-smoke-test).

The templates have jobs of their own: `pdf-check-*` runs `ci.yml`'s PDF check hand-off and its `PDF_CHECK: 'false'` switch, and `preview-site-handoff` and `preview-deploy-job` its build-to-deploy hand-off, with change detection fetching no stored credentials. `container-images` is the call to `validate-containers.yml`. `canary-watch` self-tests the canary watcher's scripts: `scripts/canary-watch.sh` against a stand-in `gh`, and `scripts/canary-drift.py` on small workflows and on the declarations file itself.

### Adding a job

- Put it beside the related jobs, and add it to `harness-summary`'s `needs:`. A job that must be skipped stays out of `needs:`, since the summary fails a skipped job; check its skip from another job, as the `pdf-check-switch-*` jobs do.
- Show that it can fail: run it once against the bug it guards, or with the assertion inverted, and say so in the pull request.
- If the job needs a file the gate would ignore, check the gate's self-test still passes.

## Containers

A pull request that changes an image builds and smoke-tests it before it can merge. The merge rebuilds the images, smoke-tests them again, and moves `:latest` only if every smoke test passes; the lecture matrix then runs against the promoted images. [CONTAINERS.md](CONTAINERS.md) describes that path and the smoke test, and [CONTAINER-VALIDATION.md](CONTAINER-VALIDATION.md) the lecture matrix and its results.

## The canary

[QuantEcon/test-actions-lecture-intro](https://github.com/QuantEcon/test-actions-lecture-intro) is a lecture repository kept for testing the actions. Its `ci.yml`, `cache.yml`, `publish.yml` and `restore.yml` are `templates/` at `v0`, run for real, with the differences [`.github/canary-drift.yml`](../../.github/canary-drift.yml) declares, and they pin `@v0`:

- `ci.yml`, on its pull requests, by hand, and on Sunday at 01:00 UTC: `restore-jupyter-cache`, `build-lectures`, and real deploys with both `preview-netlify` and `preview-cloudflare`. Off a pull request both previews deploy to `dispatch-canary`, and the run fails unless each reports `deployed` and serves the build's marker file;
- `cache.yml`, on Sunday at 00:00 UTC, on a push to `main` that changes `environment.yml`, and by hand: `build-jupyter-cache`;
- `publish.yml`, on a `publish*` tag, by hand, and on Sunday at 02:00 UTC: `publish-gh-pages`, which uploads the site, deploys it, and on a tag attaches it to the tag's release. The run fails unless GitHub Pages serves the build's marker file;
- `restore.yml`, by hand: `restore-gh-pages`, from a release that `publish.yml` made.

**Its GitHub Pages site** shows whichever deploy came last: the canary's book, from `publish.yml` or `restore.yml`, or the release gate's fixture, from `gate.yml`. So the gate and `publish.yml` each read the site back after they deploy, and compare a marker file that their own build wrote with their own commit, by content: neither reports green on the other's site, and a check by status alone would pass a Cloudflare Pages preview, which answers 200 for any path. The gate's deploy, `publish.yml` and `restore.yml` share the `pages` concurrency group, in which a run that joins while one runs and another waits cancels the waiting one, so `publish.yml`'s schedule is clear of the hours the gate is run in.

In a staged release, a branch of the canary points these at the candidate tag only for what the release gate does not reach, and once `v0` has moved the release dispatches `ci.yml`, `cache.yml` and `publish.yml` on the canary's `main`: see [Staged Releases](../../CONTRIBUTING.md#staged-releases).

**The watcher.** Nobody watches the canary's scheduled runs, and GitHub disables a public repository's schedules after 60 days with no activity in it, which leaves nothing to report. So [`canary-watch.yml`](../../.github/workflows/canary-watch.yml), here, reads the canary through the API every day, with two checks:

- **The scheduled runs** of each workflow it lists: `cache.yml`, `ci.yml` and `publish.yml`, the canary's three schedules. One that is disabled, whose newest scheduled run on `main` did not succeed, or that has not run for eight days, turns it red. For a disabled workflow, the finding gives the `gh workflow enable` command.
- **Drift.** Each of the four workflows is compared with the template of the same name at `v0` as YAML, so comments and key order do not count, and nor do third-party actions' versions, which the canary's Dependabot moves; the steps both have must run in the same order. A difference that `.github/canary-drift.yml` does not declare turns it red, and so does a declared one that no longer differs, or a declared value, a mapping or list included, that the canary no longer holds. A declared path covers everything under it, apart from an `if`, `continue-on-error` or `permissions` key, which needs a declaration of its own. And every `quantecon/actions` action the canary runs must run at `@v0`, declared or not. A release that changes a template therefore turns it red until a canary pull request realigns the copy, unless the change is to a third-party action's version or under a declared path.

On the schedule, a red verdict opens one issue, `🔴 Canary watch: …`, labelled `canary` and assigned to the logins in the `CANARY_ASSIGNEES` repository variable, or comments on the open one when that check's findings have changed. Each check keeps its own record there, so one check's state never stands for the other's. A green scheduled run notes once on the open issue that its check is green again, so the same red later is reported again.

What the drift check does not see, by design:

- **A declared path's own content.** A declaration covers the subtree under it, so a step only the canary has can change its script or inputs, or the action it runs if that is not `quantecon/actions`', and stay green.
- **New keys under a declaration with no value.** `on.pull_request` and `on.workflow_dispatch` are declared without one, so a future `v0` that adds `on.pull_request.types` or `workflow_dispatch.inputs` to `templates/ci.yml` stays green, and the canary runs without them.

### The release gate

`gate.yml` in the canary tests a candidate before `v0` moves. It is dispatched on the canary's `main` with `candidate`, a commit SHA or a `v*` tag of this repository, and refuses one that is reachable from neither `main` nor a `v*` tag, before any job that holds a secret. It checks that commit out and runs every action from it, as `uses: ./actions-repo/<action>`, on the fixture in the canary's `gate/`. The fixture's image is pinned by digest, its pages read nothing from the network, and Dependabot updates nothing in it, so a red gate means the candidate.

- **The cache build:** `build-jupyter-cache` with all three builders and nothing restored, after its four nested `uses: quantecon/actions/…@v0` lines are rewritten to the checkout, so its siblings run at the candidate. A nested call left over fails the job. It checks that every page executed, from a line each page prints, in the HTML and the PDF's LaTeX.
- **Two site builds** restore that run's caches, the execution cache as `templates/ci.yml` does and the build cache as lecture-dp's `ci.yml` does, and must restore that run's key.
- **The deploys** run in jobs of their own that execute no notebook, under environments that allow `main` only: `preview-netlify` and `preview-cloudflare` with `dispatch-alias: dispatch-release-gate`, which must report `deployed`, and `publish-gh-pages` in its `upload` and `deploy` modes. Each deployed URL must serve a marker file holding the candidate's SHA, compared by content.
- **The verdict** passes only if every job did. A red run from `main` opens or comments on a `release-gate` issue in the canary, assigned to whoever dispatched it.

`self-test: build-fails` appends a raising cell to the fixture, and `self-test: nothing-deployed` runs the previews without their alias. Each must turn the gate red. On any branch but `main` the deploy jobs are refused, so such a run is always red, and the jobs before the deploys show whether the build works.

## Locally

- **The manual's checks**: `python3 scripts/generate-docs.py --check --check-examples --actionlint "$(command -v actionlint)"`, with the actionlint release the gate pins.
- **The workflows**: `actionlint` from the repository's root, with no arguments. Both actionlint commands lint `run:` scripts only when a `shellcheck` is on your `PATH`, and `pip install shellcheck-py` into a virtual environment provides one. A shellcheck version other than the one the gate logs can report differently.
- **The actions' shell**: `python3 scripts/lint-shell.py`, with that shellcheck, or another given as `--shellcheck PATH`. It prints the version it ran.
- **A larger book**: clone a real lecture repository into `tests/local/`, which git ignores; see [tests/README.md](../../tests/README.md).
- **The images**: build them as [CONTAINERS.md](CONTAINERS.md#building-locally) shows, and run the smoke test on macOS with `containers/quantecon/tests/run-local-tests.sh`.
- **An action from a branch**: in a lecture repository, point a step at `quantecon/actions/<action>@<branch>`.

## What is not covered

- **The reusable workflows' own logic.** A called workflow runs its jobs on the caller's runners and in the caller's environment, where the harness can put no stand-in `gh` on `PATH`, and this repository has no Pages site to deploy to. So the harness checks [`deploy-release`](../user/workflows/deploy-release.md) only as a file: `actionlint`, and `generate-docs.py --check-examples` on its caller template. It is proven on the canary, or on QuantEcon/test-lecture-dp, the lecture monorepo's test copy of `lecture-dp`, in each release that changes it. It names its actions at `@v0`, so a canary caller pinned to a candidate runs the candidate's workflow with the actions at `v0`: a change that needs a new action and a new workflow releases the action first.
- **Real deploys.** No harness job deploys anywhere: that needs real sites and secrets. The release gate deploys both previews and GitHub Pages for each candidate, and the canary's pull requests, tag runs and Sunday runs deploy them too; a `deploy-cloudflare` deploy is proven only by the first consumer run after a release.
- **A filed failure issue.** The harness checks the issue's text and the guards that lead to it, but filing one needs `issues: write` and would open real issues on every run, so only an unattended consumer or canary run files one, or the canary watcher's schedule.
- **`build-jupyter-cache` exactly as shipped, at the candidate.** In the harness its siblings run at `@v0`. The release gate runs them at the candidate, but in a copy of the action with its nested calls rewritten.
- **How consumers fetch a release, before `v0` moves.** The release gate runs the actions from a checkout, so the download a consumer's `uses: …@v0` makes is first exercised once `v0` has moved, by the canary's workflows, which the release then dispatches and which run every Sunday.
- **`setup-environment` outside a container, `setup-latex`, `deploy-cloudflare` and `preview-workers` at the candidate.** The gate builds in a container and deploys to no Worker; a release that changes them stages them by hand.
- **The lecture repositories' own content**, beyond the four the lecture matrix builds.
